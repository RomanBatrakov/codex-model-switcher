# Codex Model Switcher: правила проекта

Этот файл описывает рабочие правила для Codex и разработчиков проекта.

## Назначение проекта

Плагин IntelliJ IDEA управляет локальным Codex app-server и позволяет:

- переключать модель и reasoning одним нажатием или сочетанием клавиш;
- менять настройки во всех активных чатах;
- создавать новый чат через app-server;
- выбирать и открывать сохранённый чат;
- работать с локальным WebSocket-адресом app-server.

Основной код находится в `src/main/java/com/github/romanbatrakov/codexmodelswitcher`, описание плагина — в `src/main/resources/META-INF/plugin.xml`.

## Ветки и релизы

Релизные ветки образуют последовательную цепочку, каждая растёт из предыдущей: `main` (`0.5.0`) → `0.6` → `0.7` → `0.8` → ... Никакая релизная ветка не создаётся заново от `main` — только от HEAD предыдущей уже выпущенной релизной ветки.

Запуск нового цикла:

1. Создать новую ветку от текущей финальной релизной ветки, например `0.8` от `0.7`.
2. Сразу поднять версию (см. ниже) и закоммитить `release: 0.8.0` как отправную точку цикла, запушить ветку.

Работа внутри цикла — через короткие задачные ветки:

1. На каждую задачу (фича/фикс/баг) — отдельная ветка от текущей релизной ветки цикла, например `0.8-fix-foo` от `0.8`.
2. В задачной ветке — небольшие логические коммиты только по этой задаче.
3. По готовности вливаем её обратно в релизную ветку **через rebase, не через merge-коммит**: перебазировать задачную ветку на актуальный `0.8` (`git rebase 0.8`), затем перевести `0.8` на неё fast-forward'ом (`git checkout 0.8 && git merge --ff-only 0.8-fix-foo`).
4. Задачную ветку после вливания удалить.

Это даёт внутри каждой релизной ветки чистую линейную историю без merge-коммитов и без веток, случайно ответвившихся не от той точки.

Общие правила:

- Обычные (не fast-forward) merge-коммиты не используем нигде.
- В релизной ветке каждый выпуск фиксируем отдельным коммитом: `release: 0.6.0-beta.1`, `release: 0.6.0` и т.д.
- Версию перед релизом синхронно обновляем везде, где она захардкожена: `build.gradle.kts`, `src/main/resources/META-INF/plugin.xml`, fallback-константы в коде (`CodexUtils.pluginVersion()`, `clientInfo` в `CodexAppServerClient`).
- Для опубликованного релиза создаём тег с тем же номером, например `v0.6.0`.
- Перенос завершённого цикла в `main` (если требуется) — тоже только fast-forward, без merge-коммита.

## Коммиты

- Один коммит — одно законченное логическое изменение.
- Не смешивать в одном коммите код, документацию, IDE-настройки и случайные артефакты сборки.
- Заголовок короткий, конкретный и желательно не длиннее 50 символов:
  - `security: ...` — безопасность;
  - `fix: ...` — исправление поведения;
  - `feat: ...` — новая возможность;
  - `build: ...` — сборка и артефакты;
  - `docs: ...` — документация;
  - `release: ...` — выпуск версии.
- Если причина изменения не очевидна, добавлять тело коммита через пустую строку после заголовка.
- Перед коммитом проверять `git diff --check` и просматривать список staged-файлов.
- Не коммитить секреты, токены, локальные пути пользователя, временные файлы, `.DS_Store`, `.gradle/`, `build/` и `.intellijPlatform/`.
- Локальные изменения пользователя сохранять и не включать в коммит без явного разрешения.

## Безопасность

- App-server должен использовать только loopback-адрес: `localhost`, `127.0.0.0/8` или IPv6 loopback. Публичные и произвольные DNS-адреса запрещены.
- Не возвращать fallback на `codex` из `PATH`: запускать только проверенный абсолютный путь к исполняемому файлу Codex.
- Для plugin-managed app-server использовать capability-токен, созданный случайно на каждый запуск. Токен хранится во временном owner-only файле, не попадает в Git и не выводится в команду открытого текста.
- В CLI-транзитах передавать токен только процессу Codex; не экспортировать его на всю терминальную сессию.
- Идентификаторы чатов принимать только в полном UUID-формате и всегда shell-экранировать перед запуском терминальной команды.
- Модель и reasoning валидировать по длине и допустимым символам/значениям до отправки в app-server или shell.
- Ограничивать размер WebSocket-сообщений, число страниц/чатов и очищать зависшие запросы после таймаута.
- Ошибки для UI обрезать и очищать от переносов строк; не показывать необработанные локальные пути и большие сырые ответы сервера.
- Не добавлять сетевые подключения, телеметрию или хранение секретов без отдельного решения и документации.

## Проверка изменений

Перед каждым логическим коммитом:

```bash
git diff --check
```

Для сборки на macOS с JDK 25:

```bash
JAVA_HOME=/Users/roman/Library/Java/JavaVirtualMachines/temurin-25.0.4/Contents/Home \
GRADLE_USER_HOME=/tmp/codex-gradle-home \
./gradlew test buildPlugin
```

Если Gradle Wrapper ещё не добавлен в ветку, использовать установленный Gradle с теми же `JAVA_HOME` и `GRADLE_USER_HOME`.

Перед релизом дополнительно проверить:

1. версию в Gradle и `plugin.xml`;
2. содержимое ZIP из `build/distributions`;
3. отсутствие секретов и временных файлов в JAR/ZIP;
4. чистоту staged-списка;
5. линейность истории (`git log --graph --oneline`).

В проекте на текущий момент нет автоматических тестов (`test` может завершиться как `NO-SOURCE`), поэтому успешная компиляция и упаковка не заменяют ручную проверку в IntelliJ IDEA.

## Рабочий цикл изменения

1. Переключиться на ветку цикла (`0.6`) и проверить состояние.
2. Сформулировать одну небольшую задачу.
3. Внести минимальное изменение и проверить diff.
4. Запустить компиляцию/тесты/упаковку, если это относится к изменению.
5. Сделать отдельный понятный коммит.
6. Перед выпуском обновить ветку через rebase на `main` и провести финальную проверку.
7. После fast-forward в `main` создать `release:`-коммит и тег.
